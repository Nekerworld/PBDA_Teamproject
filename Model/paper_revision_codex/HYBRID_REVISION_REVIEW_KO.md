## 4. 우선순위가 높은 수정 후보

### P0: 최종 재정렬까지 ALS+BPR 신호를 유지

승원 `model.py:638`의 ReRanker는 `FactorScorer.scores()`에서 ALS, BPR, combined를 받는다. 그러나 668행 부근에서 `als, _, retrieval`로 BPR를 버리고, 674행에서 `als[candidates]`를 GNN과 합친다. `experiments.py`의 validation 설정 탐색도 같은 방식이다.

논문의 수식 6은 ALS+BPR 후보 점수이며 수식 8은 이 후보 점수와 GNN의 결합이다. 현재 코드에서는 후보 포함 여부에만 BPR가 반영되고 최종 순위에는 ALS만 남는다. 특히 저장 결과에서 BPR가 ALS보다 강하므로 우선 검증할 이유가 충분하다.

제안: 최종 MF 입력을 combined 후보 점수로 바꾸고 validation 탐색과 실제 추론을 함께 맞춘다. 기존 ALS-only와 수정 MF-combined를 **동일 후보·동일 GNN·동일 gamma**에서 비교한다. 이는 BPR 복구 효과를 확인하는 대조 실험이며 우위를 보장하는 변경은 아니다.

### P0: IF가 구매 신호를 없애는 경로를 해결

80:20 기존 증거에서는 필터 전 구매 17,864건이 IF 단계에서 전부 제거됐다. IF와 core를 거친 최종 데이터에는 구매 0건, 장바구니 320건만 남는다. 원시 이벤트의 49.64%, 필터 전 학습 이벤트의 62.05%가 IF에서 제거된다. 90:10 로그에서도 구매 20,326건이 최종 0건으로 사라진다. 따라서 80:20으로 바꾼 뒤에만 생긴 현상으로 설명할 수 없다.

현재 IF 입력은 17개 특징 표 전체가 아닌 data_protocol.py의 9개 IF_FEATURES다. event_code_mean/std가 들어 있어 드문 구매 행동이 이상치 판정에 영향을 줄 가능성이 있다. 기존 학습 구간 특징 제거 실험은 원래 9개 특징에서 구매 0건 유지, 행동 코드 평균·표준편차 제외 시 3,476건 유지, 나머지 14,388건 제거를 기록한다. 행동 코드가 기여하지만 유일한 원인이라고 할 수 없다.

제안: IF 없음 / 기존 IF / 행동 코드 제외 IF를 같은 시간 분할·평가 정답에서 비교한다. 이상치 상품의 모든 행동을 삭제하는 현재 설계가 목적에 맞는지도 검토한다. IF 없는 조건을 본실험으로 채택한다면 변경 이유와 시점을 기록하고 원고 Methodology도 수정한다. 사용자가 아직 승인한 조건으로 간주하지 않는다.

### P1: 후보 누락과 재정렬 실패를 먼저 나눠 진단

GNN은 MF 후보에 없는 정답을 되살릴 수 없다. 먼저 validation에서 C=500/1000/2000/5000의 후보 recall과 후보 내 완벽 정렬 상한을 측정한다. 정답이 후보에서 빠지면 후보 생성 문제, 후보에 있지만 Top-50 밖이면 재정렬 문제다. 상한은 진단용이며 실제 모델 성능이 아니다.

제안: ALS+BPR blend와 ALS 상위 후보·BPR 상위 후보의 합집합을 같은 총 후보 수에서 비교한다. 합집합은 각 모델의 후보 할당을 보장한 뒤 중복 제거·보충해야 한다. 다시 ALS 점수만으로 잘라 버리면 BPR 고유 후보를 확보한 의미가 사라진다. 후보 수가 커지면 GNN 점수 계산 비용도 함께 측정한다.

### P1: 탐색 범위와 부분 재정렬의 제약 제거

승원 experiments.py의 MF 가중치 탐색은 0.6~1.0에 치우쳐 있다. GNN 비중이 큰 설정을 충분히 확인하지 않는다. 우선 0~1 전체를 넓게 탐색하고, 두 성분이 실제로 기여하는 내부 최적점인지 검증한다.

recommendation_scoring.py의 rerank_m은 ALS 상위 M만 재정렬하고 나머지를 그 아래에 고정한다. GNN과 BPR가 선호하는 상품을 구조적으로 막을 수 있다. 전체 후보 재정렬을 기준으로 두고 부분 재정렬은 비용 절감 실험으로 분리한다.

`gate` 구현은 `ALS_norm + (1-w)*(GNN_norm-ALS_norm)`이므로 대수적으로 minmax 가중합과 같다. 독립된 새 결합 방법으로 해석하거나 두 개의 방법이 같은 성능이라고 과장하면 안 된다. RRF와 minmax는 실제 다른 결합 방식이므로 비교 가치가 있다.

### P1: GNN을 재정렬 목적에 맞춰 학습

현재 GNN 학습 음성은 uniform이고 최종 임무는 MF가 높게 평가한 후보 안에서의 순위 결정이다. 두 분포 차이를 줄이는 방법으로 MF 후보 기반 hard negative와 uniform negative의 혼합을 제안한다. 학습에서 관측한 양성은 음성에서 제외하고, hard negative를 전부 사용하지 않아 오표기·과도한 편향 가능성을 줄인다.

단독 LightGCN NDCG가 가장 좋은 checkpoint가 Hybrid에 가장 좋은 checkpoint와 같다는 보장은 없다. standalone과 Hybrid의 validation 선택을 각각 수행하되 단독 baseline도 충분히 튜닝한다. 동일 GNN 가중치의 full-catalog 결과와 후보 재정렬 결과를 추가하면 결합 효과를 더 명확히 설명할 수 있다.

### P1: gamma의 목적과 효과를 분리

논문 수식 9의 gamma는 재고 상품 점수에 곱해진다. 관련성 정답과 재고 효용이 다르면 강한 부스팅이 NDCG/Recall을 낮출 수 있다. gamma=1을 기준으로 민감도를 보고하고 validation에서만 선택한다. gamma<1은 재고 부스팅이 아니라 재고 상품 감점이므로 해당 결과를 선택하면 용어와 해석도 바꿔야 한다.

모든 후보의 available이 같으면 순위는 변하지 않는다. 상품별 available 분포, 알 수 없는 값 처리, 시간에 따른 변경 여부도 확인한다. 학습 종료 시점 상태만 쓰는 경우 시험 시점 실시간 재고를 안다고 표현하지 않는다.

## 5. 데이터 누수와 논문 수정에서 구분해야 할 것

학습 데이터의 일부를 validation으로 분리하는 것 자체는 정상이다. 문제가 되는 것은 validation 관계가 학습 손실의 양성으로 쓰이거나, 이번처럼 행동 관계 예측 실험에서 정답 관계가 메시지 전달 그래프에 들어가는 경우다. 단순히 미래 행동이 존재한다는 사실만으로 모든 transductive 실험을 누수로 부르면 안 된다.

past_code.py는 전체 그래프 adjacency를 만든 뒤 상호작용을 train/validation으로 나눈다. 기존 복원 증거는 train 557,222쌍, validation 139,306쌍이며 두 쌍 집합의 직접 교집합은 0이지만 validation 139,306쌍 모두가 전파 그래프에 포함됐음을 기록한다. 이를 손실 학습 쌍이 직접 중복됐다는 주장과 구분한다. 원래 투고 당시 파일은 덮어써졌다는 대화가 있어 이 복원 결과가 당시 실행의 완전한 증거는 아니다.

제안 프로토콜은 전체 시간순 outer train/test를 정하고, outer train 안에서 다시 시간순 inner train/validation을 나누는 방식이다. IF·특징·그래프·음성 채굴은 해당 학습 구간만 사용한다. validation으로 설정·epoch를 고정한 뒤 outer train으로 재학습하는 것은 정상이며 outer test를 쓰는 것과 다르다. 기존 test를 이미 여러 번 확인한 사실은 남겨야 하며 완전히 미공개 시험이라고 표현하지 않는다.

논문은 속성·카테고리 이종 그래프로 맥락을 반영한다고 서술하지만 현재 revision 기본 설정은 bipartite이고 InfoNCE를 사용한다. 이종 그래프를 복원할지, 이분 그래프를 쓰고 주장을 수정할지는 아직 결정되지 않았다. 실제 구현과 선택한 조건에 맞춰 수식·구조도·학습 목적·기여를 함께 고쳐야 한다. ID 임베딩 모델의 미관측 사용자·상품에 대한 cold-start 해결 주장도 근거가 없다.

## 6. 권장 실험 순서와 판정

1. 분할·평가 사용자·정답·후보 catalog·반복 추천 허용 여부를 고정하고 manifest의 실제 경계와 설정 불일치를 해소한다. 공통 80:20은 대화에 나온 방향이지만 사용자 최종 합의로 간주하지 않는다.
2. 같은 조건에서 기존 구현을 보존하고 BPR 신호 복구만 비교한다.
3. IF 비교를 통해 구매 보존·사용자 커버리지·모든 baseline의 변화를 본다. IF만 바꿨을 때 Hybrid 고유의 이득으로 해석하지 않는다.
4. 후보 recall·후보 내 oracle·MF/GNN 적중 교집합을 보고 후보 수와 생성법을 선택한다.
5. 결합 가중치·RRF/minmax·전체/부분 재정렬·gamma를 validation에서 선택한다.
6. 개선 여지가 남으면 MF 기반 혼합 음성으로 GNN을 학습한다. 같은 checkpoint의 GNN 단독 비교도 포함한다.
7. 선택을 고정한 뒤 seed 42·43·44로 최종 실행하고 @10/@30/@50, 평균·표준편차, 사용자별 paired 차이, 실행 시간을 제시한다. 세 seed를 세 독립 데이터셋으로 해석하지 않는다.

Hybrid와 가장 강한 baseline 각각의 NDCG·Recall 차이를 제시한다. 두 지표를 함께 최적화하려면 validation에서 각 지표의 최강 baseline 대비 상대 개선 중 작은 값을 선택 점수로 사용할 수 있다. 한 지표 하락을 다른 지표 상승으로 가리지 않는 기준이다. 기준은 시험 결과를 보며 바꾸지 않는다.

현재 80:20 no-IF 기존 증거의 평가 사용자 854명 중 학습 사용자 벡터 보유는 429명, 미보유는 425명, 도달 가능한 정답이 있는 사용자는 409명이다. 409를 학습 사용자 수라고 쓰면 안 된다. 원래 정답 분모와 미보유 0점을 유지한 평균, 조건부 warm 결과를 따로 보고한다. 추천 가능한 catalog의 구조적 한계도 모델 순위 실패와 분리한다.

## 7. 추가로 필요한 자료: 우선순위

### 가장 중요: 투고 당시 실행의 원본 보존 자료

가능하면 당시 Git commit/ZIP, 정확한 실행 명령, requirements, 전처리 train/validation/test 파일, 사용자·상품 매핑, GNN graph edges, 저장 임베딩, 사용자별 추천·평가 파일을 제공하면 좋다. 전부 없으면 남아 있는 파일만 있어도 된다. 재구성 데이터와 실제 당시 데이터가 같은지, 원래 .3710 NDCG/.7113 Recall 등의 수치가 어떤 평가에서 나왔는지를 확인하는 핵심 자료다. 현재 덮어쓴 폴더나 다시 만든 legacy ZIP은 당시 실행 보존본을 대체하지 못한다.

### 원고를 실제 수정하려면: 편집 원본

PDF에 대응하는 LaTeX/Word, 원본 그림·표 파일이 필요하다. 분석에는 현재 PDF로 충분하지만 구조·수식·실험 전체를 일관되게 고치려면 편집 원본이 유용하다.

### 재고 기여를 강하게 주장하려면: 시간 정보와 의미

available이 실제 판매 가능 여부인지, 품절인지, 누락값인지에 대한 설명과 가능하면 timestamp별 상품 상태 이력이 필요하다. 현재 raw property 파일로 일부 확인할 수 있지만 실제 재고 수량·시험 시점 재고 정답을 대신한다고 단정할 수 없다.

### 있으면 연구를 더 강하게 만드는 자료

별도 시기 또는 다른 데이터셋, 구매 의도·노출·세션 정보가 있으면 추가 일반화 검증과 음성 표본 해석에 도움이 된다. 기존 raw RetailRocket events.csv, item_properties_part1/2.csv, category_tree.csv는 현재 프로젝트에 있으므로 다시 제공할 필요는 없다. baseline 개선 분석과 새로운 validation 실험을 시작하는 데 외부 데이터가 필수는 아니다.

봇 판정을 유지하려는 경우에만 검증된 bot label이나 별도 검증 근거가 필요하다. 대화에서 교수님은 bot 표현을 빼는 방향을 제시했으므로, 해당 주장을 빼면 이 자료를 굳이 수집할 필요는 없다.

## 8. 교수님께 설명할 핵심

현재 성능 저하는 단일 원인으로 확정되지 않았다. 기존 비교 조건 혼용과 그래프 누수 문제를 바로잡는 과정에서 IF의 구매 소실, 최종 재정렬의 BPR 누락, 후보와 재정렬의 목적 불일치가 별도로 드러났다. 순서대로 통제 비교하면 Hybrid가 어떤 조건에서 실제 이득을 내는지 확인할 수 있다. 성능 순위를 미리 보장하기보다 이 구체적인 수정 근거와 동일 조건 비교 결과로 논문의 핵심 주장을 다시 검증하는 것이 필요하다.
